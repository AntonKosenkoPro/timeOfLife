## Goals / Non-Goals

Goals: one Widget Extension hosting the timer `ActivityConfiguration`; request/end wired to the existing Start/Stop call sites; Stop intent reusing the `manual` save path; deep link to Track; Saved-then-dismiss ending.
Non-goals (design-level): no `ControlWidget` in this extension; no push tokens; no per-second `update()` loop; no shared-`Theme` refactor beyond what the extension needs to render (see D4); no sync from the extension.

## Decisions

**D1 — Attributes vs ContentState split.** `TimerAttributes` (static: exact text, first-category icon symbol) + `ContentState` (dynamic: `startedAt: Date`). Elapsed renders via `Text(timerInterval:)` so the system ticks with zero updates. Alternative (pushing elapsed strings via `update()` every second) rejected: rate-limited, battery-costly, and the sole source of avoidable `stale` transitions. The compact timer carries an explicit `.frame(width: 52)`: the timer view has no intrinsic size — it fills any proposal (stretching the pill edge-to-edge) and collapses to zero under `fixedSize` (both observed on-device; same root cause as Mobileraker #273). Twin-`overlay` hugging was tried per device feedback and reverted: it does not constrain in the compact slot (pill went wide again), while the frame era was explicitly confirmed good. 52pt fits H:MM:SS in the ~52–62pt slot; monospaced digits keep shorter values stable. The expanded timer border instead hugs dynamically: the live view has no intrinsic size, so a hidden static twin in the same format (`TimerClock.liveStyle`) sizes the capsule via `overlay` (overlay content takes no part in layout — a `ZStack` sizes to every child including the stretchy live view and goes full-width again) — no fixed points (Dynamic-Type-safe), growing with the digits. The twin freezes at render time, so a phase crossing without a re-render keeps the previous width until the next render (text may spill past the border, never clipped).

**D2 — Singleton guard.** Before `request()`, query existing activities for our attributes type; reuse or `end()` the stale one first. Alternative (request blindly) rejected: duplicate Islands after crash-relaunch (draft survives crashes by design).

**D3 — Stop intent writes through `LocalStore`.** The intent resolves the active account file (same resolver the app uses) and calls the existing stop transaction (`createEntry` + `clearTimerDraft` + outbox row); `source='manual'`. Alternative (new `liveactivity` source) rejected by user decision — no provenance, History shows no "via" label. Alternative (intent writes GRDB directly) rejected: violates the single-chokepoint invariant.

**D8 — The intent saves + signals; the app ends with the Saved card.** The attributes type lives in the shared `LifioLiveActivityCore` dynamic framework (single module — still the right home for the contract), but `ActivityKit` enumeration is scoped by calling process: the extension's `activities` is always empty even with a unified type (device-proven over two builds: `ending 0 active` with a live banner, type names identical). Direct end from the intent is therefore impossible — no production path ends activities from an extension; Apple's docs frame start/update/end as *"in your app"* operations. So the intent posts the `LiveActivitySignal` Darwin notification (with the true duration) and the app ends with the Saved final state + timed dismissal: immediately via the Darwin handler when background-alive, otherwise on the next foreground/load sweep (which then shows the Saved card). Until that contact the banner keeps ticking — documented limitation, not a bug. Crash hygiene stays: a kill that leaves a live Island with no draft is reaped by the same sweep with nil duration (silent immediate dismiss, no invented duration), and Track `load()` reconciles a draft-less `.running` state the same way. Only `.active` activities are touched — an `.ended` Saved card keeps its own dismissal.

**D8 follow-up — entry-recency heuristic + background reap chain.** Two mechanisms close the "banner keeps ticking until the app gets CPU" gap (device-proven: after a widget Stop with the app suspended, no contact arrived and the finished run kept ticking):
1. *Heuristic (deterministic, tested):* `TimerService.endOrphanedActivities(knownDurationSeconds: nil)` no longer passes nil through — when the draft is gone it consults the most recent entry (`LocalStore.latestEntry()`, `LIMIT 1`), and when that entry ended within the last 10 minutes delegates with its true `durationSeconds` (Saved card, nothing invented); otherwise nil as before (true crash/ancient stop → silent immediate dismiss). Self-consistency: an in-app stop ends activities synchronously in `runEnded`, so a later sweep finds nothing live and no-ops; a crash between save and end leaves draft-nil + recent entry + live activity, which CORRECTLY yields the Saved card. Draft present → early return, unchanged; read errors fail closed, unchanged. No marker file or new state — the entry is the record.
2. *BG chain (async wake):* `BackgroundReapScheduler` (`Core/Background/`) cancel-then-submits a `BGAppRefreshTaskRequest` (`com.antonkosenko.timeoflifeapp.reap-check`, ~60s hint) on every Start and cancels on every definitive end (`stopTimerDraft`, external-stop handling); the handler registered once in `AppContainer.init` (runs on background launches too) runs the Part-A funnel, then re-arms only while a draft is still live — a finished run ends the chain and the next Start re-arms it. Plist carries `UIBackgroundModes=fetch` + `BGTaskSchedulerPermittedIdentifiers`; the Background Modes capability is declared in `project.yml` `SystemCapabilities` (same regen-safe pattern as App Group/SIWA).
*OS-timing honesty:* BG fire time is system-determined — typically minutes, never guaranteed, and unverifiable in the simulator. In the worst case (throttled background, BG disabled) the banner may still tick a while after a widget Stop; the first app contact (Darwin signal, foreground, load) clears it via the heuristic. Device verifies.

**D4 — Extension theming.** As built: no custom palette — system default activity background; banner face is title icon + headline name + subheadline monospaced live timer with 8pt vertical + 8pt horizontal padding (device-tuned). Stop controls use `LiveActivityTheme` (minimal extension-safe subset mirroring `Theme.danger`/`Theme.textOnAccent` as system-red/white, no raw literals in the widget) as flat red shapes. Liquid Glass was attempted twice and reverted, both device-verified: `.glassProminent` tinted renders as a flat disc, and an explicit red-tinted `glassEffect` container drops the whole button from the render — third-party activity renders are frozen archives with no live-compositing engine, so refraction is system-only. A translucent `activityBackgroundTint` was equally invisible (opaque base). Flat + Theme tokens is the ceiling; banner/island containers stay system-default. Full `Theme` is NOT shared: its colors resolve via `Color("…", bundle: .main)`, and `.main` in the appex is the extension bundle, which ships no asset catalog — sharing it would silently break or force-duplicate the catalog. AoD-probe leftovers removed (`maskedCoarse` + tests, `AodTint`/`AodAccentable`, debug border, luminance-gated Stop — Stop is dimmed+inert under AoD, see D7). The shared `Localizable.strings` ship in the extension bundle (single source); data-only contract types (`TimerActivityAttributes`, `TimerClock`, `LiveActivityStrings`) live in the shared `LifioLiveActivityCore` framework linked by both sides (single module — see D8). App-only modules (`Theme`, `L10n`) stay out. The `bump-ios-deployment-to-18` archive's target-removal notes cover the `xcodegen` side (capabilities block, `postGenCommand` normalization — extended to multi-target in `normalize-system-capabilities.py`).

**D5 — Navigation.** `widgetURL(lifio://track)` on compact/minimal/banner; `Link` + `widgetURL` in expanded (Go row). `RootView` handles the URL by selecting Track. Default system open (no URL) rejected: must land on Track, not relaunch state.

**D6 — Dismissal.** `end(finalContent, .after(now + T))`, T tuned in testing (~6s starting point). `.immediate` rejected (no Saved moment); `.default` rejected (4h linger). Island collapses at `end()`; banner shows `✓ Saved <duration>` until T.

**D7 — Dimmed rendering.** The banner elapsed is a live ticking timer (`Text(timerInterval:)`); the system dims it on Always-On itself, like Apple's Timer face. No luminance branch, no accent wrappers, no tint. Stop is dimmed+inert under AoD (`isLuminanceReduced` → disabled + 40% opacity — pocket-stop protection) and demands Face ID/passcode on a woken locked phone (`requiresLocalDeviceAuthentication`); unlocked taps run immediately (D8).

**AoD blank postmortem (device-verified):** the dimmed banner showed redaction placeholders regardless of content — including fully static giant text — because of a device setting, not rendering. Syslog verdict at lock: `Security policy yielding placeholder content: Keybag locked and user's Setting is set to hide widget data; Policy decided must show placeholder` (`reason: enteringAlwaysOn`). Fix: Settings → Face ID & Passcode → Allow Access When Locked → Live Activities ON. Device smoke (tasks 4.3) requires this setting. Dead activities from reinstalls linger invisibly in the renderer (`activity-archive doesn't exist` noise) and expire on their own — ignore. The extension target keeps one `sources:` list only (a second key replaces the first — this shipped an appex with no executable), and shared strings ride as explicit `buildPhase: resources` file entries (`resources:` globs are silently dropped for paths the app target already owns — this rendered raw keys on every face).

## Risks / Trade-offs

- [Extension reads a file mid-migration] → Extension opens read-only and fails to the graceful face; all writes stay app-side. Mitigation: never open read-write from the extension.
- [Stop tapped during an in-flight app Stop] → Second stop finds no draft; intent treats missing draft as success (idempotent, mirrors 404-as-success in sync).
- [Two activities squeeze (music + timer)] → Minimal face must survive at icon size; covered by spec scenario, verify with a music session in testing.
- [Widget-SwiftUI subset] → No `TimelineView`, limited modifiers; keep faces to `Text`/`Image`/`Button`/`Link` + `DynamicIslandExpandedRegion`.
- [`xcodegen` regen wipes capabilities] → Declare App Group + deep-link scheme in `project.yml`, run `generate`, verify attendant `SystemCapabilities` (same failure mode as the SIWA incident).

## Migration Plan

No migration: additive target + additive `timer_state` readers; existing drafts unaffected. Rollback = remove extension target (single `project.yml` revert + delete sources). No backend deploy.
