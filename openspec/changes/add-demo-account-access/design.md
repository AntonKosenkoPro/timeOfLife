## Context

See `proposal.md` for motivation and scope. Current `backend/internal/handlers/auth.go` handles email OTP, requires `X-Device-Id`, and delegates successful login to ordinary token issuance. `internal/auth/otp.go` hashes short-lived codes with SHA-256; `internal/ratelimit/ratelimit.go` holds per-process IP/email buckets. Neither provides safe long-lived review-code protection. Backend account deletion is transactional in both store implementations.

The shipping iOS `AuthValidator` accepts six digits. `OtpEntryViewModel` has only a 30-second **resend** cooldown, not a verification expiry timer; existing error localization supports `invalid_otp` and `rate_limited`. No client demo branch or new route is needed. The new capability composes existing `device-sessions`, `account-bound-store`, and `account-deletion` contracts without changing them.

## Goals / Non-Goals

**Goals:** keep the current app binary compatible; make every security-sensitive decision server-authoritative; reserve attempts atomically across replicas; keep code lifecycle separate from ordinary token lifetimes; give the owner an auditable shutdown procedure.

**Non-Goals:** generic password authentication, a demo privilege/role, different reviewer features, account deletion exemptions, a shared mailbox service, general durable OTP-rate-limit replacement, new observability infrastructure, or automatic production activation. Existing quota/picker work remains separately required before release; this feature adds no quota bypass.

## Decisions

### 1. One configured binding; reuse the current email path

Use server configuration `REVIEW_ACCESS_ENABLED` (default false), `REVIEW_ACCOUNT_ID`, `REVIEW_ACCOUNT_EMAIL`, `REVIEW_CODE_VERIFIER`, and `REVIEW_CODE_KEY`. The ID and email are configuration, not hardcoded source constants. The initial intended binding is in the proposal; production identity/verified/email-provider state must be checked again before activation. Enabled configuration requires a valid UUID, canonical valid email, exactly one SHA-256-sized hex verifier, and an independent cryptographically random 32-byte key encoded as 64 hex characters. Reject malformed configuration without printing values. Disabled deployments do not require review secrets.

Canonicalize exactly as the ordinary email path; never collapse Gmail dots or plus aliases. Enabled review-address selection happens before ordinary account upsert, OTP persistence, or email delivery. Requests for that address return the ordinary 202 body even if its expected UUID no longer exists or the binding fails eligibility. No runtime database mismatch is allowed to bring down unrelated authentication: deny only review authentication and emit a safe diagnostic. Verify requires an existing verified email-created account with both fields matching. No `SetUserVerified`, Apple lineage, account upsert, or ordinary OTP fallback is permitted on this branch. Validate `X-Device-Id` and the existing request schema first.

For other addresses and when disabled, leave existing authentication behavior untouched. Stale ordinary OTP records cannot authorize the enabled review address, and resends never rotate the reusable code. No marker or new body field announces review-account state. This preserves response-shape enumeration closure; it does not promise perfect timing indistinguishability or hide the identity of a privately supplied review account.

**Alternative rejected:** a new `/auth/demo/verify` route would require client routing/new error handling and provide no benefit to the existing code-entry flow. A universal code or email-domain rule would extend the exception to real accounts.

### 2. Dedicated keyed verifier, not a permanent ordinary OTP row

Keep the verifier and dedicated key in protected deployment configuration, never in `otp_codes`. Define the verifier as HMAC-SHA256 over unambiguous purpose/version, immutable UUID, canonical email, and code components (fixed domain tag followed by NUL-delimited canonical fields). Compare decoded fixed-size MACs in constant time. The key is independent of JWT, refresh recovery, account-status, and Apple secrets, so their rotations cannot accidentally change review login. No new cryptographic dependency is planned; confirm standard-library API details at apply time.

Provide a small local operator utility under `backend/cmd/review-access` to compute the verifier from the binding, dedicated key, and privately supplied code on stdin, never command-line arguments. It validates exactly six ASCII digits, produces only the verifier through an explicitly protected output destination, and never echoes the code or key. The owner chooses a uniformly random code using approved private credential tooling; no predictable example/default code is shipped. Runtime configuration contains no plaintext review code. The owner stores the code in a password manager and Apple's private Review Notes. Verifier/key outputs and deploy commands must remain out of shell tracing, CI logs, and checked-in files.

This does not make a six-digit static secret strong: a combined key/config compromise permits fast enumeration. It does prevent the operational DB or an unkeyed SHA-256 digest from being a standalone offline guessing oracle. Rotating the dedicated key requires recomputing the verifier in the same deployment.

**Alternatives rejected:** raw code in environment/source; plain SHA-256; reusing the ordinary OTP's far-future expiry. A long high-entropy reviewer password would be stronger but does not fit the shipping six-digit field; a secured OTP portal adds another service and reviewer steps.

### 3. Durable rolling budgets, with atomic admission before comparison

Add a narrow `review_auth_attempts` table with account UUID foreign key, unique attempt ID, admitted timestamp, and `(user_id, admitted_at)` index. It stores no code, IP, device ID, email, or outcome payload. Apply an additive migration using the next available migration number; cover Postgres and the SQLite test adapter. Account deletion must explicitly delete these rows by user UUID inside the existing purge transaction in both stores, respecting the current ordered child deletes; do not rely on FK cascades or SQLite FK pragmas. Include rollback/parity tests.

Use a store operation to validate the current account binding and reserve an attempt in one transaction. Acquire the account-row lock first, matching the existing deletion/refresh lock order; use equivalent writer serialization in SQLite. With authoritative store time, prune that account's timestamps at or before `now - 24h`, count admissions strictly newer than `now - 15m` and `now - 24h`, and insert only if both counts are below 5 and 20. Commit the reservation **before** comparing the code or issuing sessions. A crash, failed comparison, or later token-issuance error still consumes capacity. A budget denial does not append or move timestamps, preventing unauthenticated lockout extension without a newly admitted attempt. Calculate `Retry-After` as the ceiling in seconds until **both** windows have capacity. Tests pin boundary inclusion and time arithmetic.

Keep the current IP/email verification limit as additional defense; an IP rejection need not reserve an account attempt because it does not evaluate the code. Neither a correct code nor another IP/device, resend, enabled toggle, or verifier/key rotation clears attempt history. Store failure returns the existing internal/service error, never an in-memory fallback. Re-check current account lifecycle through the ordinary token-issuance fence after admission; deletion between admission and issuance must prevent a usable successor. Active admissions for this single account are bounded at twenty per 24 hours; opportunistic per-account pruning avoids a new sweeper service. Idle history is harmless, ages out semantically, and is removed on next admission or account purge.

**Alternative rejected:** another in-memory token bucket resets across restart and is multiplied by replicas. Handler-side read-then-increment races permit excess guesses. A single short window permits sustained guessing over a permanent credential, so a second daily budget is included. These are deliberate initial operational limits, not OWASP-prescribed numbers.

### 4. Ordinary sessions and full account functionality

On correct code, call the existing ordinary email-session issuance path with the normal device identity and account-lifecycle fences. Do not add a privileged claim, special session TTL, Apple identity, authorization bypass, or separate store namespace. Refresh/recovery/logout/account-status and same-account sync remain unchanged. Sessions still expire even though the review code does not. Existing `401 invalid_otp`, `429 rate_limited`, validation, and service-error envelopes avoid client changes; `Retry-After` aids tooling even though current iOS does not read it.

The reviewer can mutate or delete the shared account. Do not disable Account → Delete or auto-recreate the UUID to preserve credentials. Purge removes attempt rows and credentials atomically; the enabled reserved review address returns 202 but cannot authenticate afterward. The owner must explicitly re-provision synthetic content and update the configured UUID if replacement is needed. Once review access is disabled, ordinary same-email registration may create a new UUID; it inherits no exception. Existing account-specific local cleanup/status behavior remains authoritative.

**Alternative rejected:** making the account read-only or exempt from deletion would hide real app functionality and complicate App Review. A data-reset job could overwrite reviewer work and is outside this change.

### 5. Deployment-controlled lifecycle and minimal telemetry

Wire the new configuration through `.env.example`, config/server DI, Docker/deploy environment propagation, and `.github/workflows/backend.yml` secret rendering. New vars must not silently disappear when deployment rewrites `.env`. Disabled config stays the shipped default. Syntax validation is local; activation requires an owner-approved private identity/data check and credential placement. Do not run this plan against production or choose/store an actual code during proposal or ordinary automated tests.

The operator runbook documents fleet-wide enablement, code/key rotation, disablement, verification, and review-account-only refresh/recovery revocation. Extend the private operator utility with a UUID-confirmed revoke-sessions operation that reuses the existing store `RevokeAllUserSessions` primitive, which already atomically revokes refresh tokens and consumes recovery receipts in both stores. Add no parallel revocation SQL or new lock order; no old receipt may recover a revoked session. It must not erase account data, alter other accounts, or clear throttle history. Complete deployment across all serving instances before claiming a change effective. Stop new logins first, then revoke refresh/recovery credentials; explicitly allow for already in-flight issuance and repeat verification/revocation after the deployment quiesces. Existing access JWTs can remain usable until their ordinary expiry (at most 15 minutes); no immediate kill switch for access tokens is promised. Re-login via an ordinary mailed OTP after disablement is expected, not a bypass of shutdown.

Emit existing structured backend diagnostics for bounded review outcomes (`success`, `invalid`, `throttled`, `unavailable`, binding mismatch) without secret/account identifiers, request bodies, or high-cardinality labels. Reuse existing telemetry; add no new dashboards, external SDK, or always-on alert dependency. The runbook requires checking these outcomes before submission and during review, contacting the owner if throttling/deletion blocks review, keeping access available throughout intended review/follow-up, and explicit disable/rotate decisions rather than an unattended expiry timer. Private Review Notes explain that no Gmail sign-in is needed and that the account is shared synthetic data.

## Risks / Trade-offs

- [A permanent six-digit secret has about 20 bits of entropy and can eventually be guessed] → synthetic data only, keyed verifier, strict persistent budgets, private distribution, monitoring, and owner-controlled rotation/disablement. This remains a consciously weaker credential, not general authentication best practice or NIST assurance compliance.
- [Account-wide budgets permit denial of reviewer access] → finite rolling windows, denied requests cannot extend them, `Retry-After`, pre-submission smoke, monitored owner recovery. Correct codes do not bypass exhausted budgets. Do not weaken controls for a special reviewer IP.
- [Shared reviewers see each other's changes or delete the account] → disclose shared synthetic data, preserve ordinary deletion, and require explicit owner recovery; no automatic destructive reset.
- [An enabled stale backend or unrevoked refresh family keeps access alive] → complete fleet deployment, revoke all review-account refresh/recovery records after quiescence, verify, and state the residual JWT window.
- [Operational key + verifier disclosure] → the small code space can be enumerated; secure CI/config, avoid logs, and rotate/revoke on exposure. HMAC is not protection against full server compromise.
- [Later device quotas block a reviewer] → #46 remains a release gate; re-check compatibility when its policy lands, without inventing a quota exemption here.
- [Policy or standard-library/SQL behavior changes before apply] → refresh the cited research and run both SQLite and real-Postgres race/lifecycle tests before enablement.

## Migration Plan

1. Rebase fresh `origin/main` and complete apply-time research; write regression tests against the current ordinary flow and proposed exception before implementing it. This is a feature, not a bugfix requiring a simulated Gmail challenge reproduction.
2. Add the attempt table/index and tested account-purge integration; use additive expand-contract SQL only. Previous images must continue to run; no destructive rollback migration.
3. Deploy code with `REVIEW_ACCESS_ENABLED=false` and prove normal OTP/Apple/session/deletion paths unchanged. Wire protected configuration without printing secrets. Keep review access disabled until explicit owner activation approval.
4. In a separate owner-controlled operation, confirm exact UUID/email/provider and synthetic data, privately choose code/key and compute verifier, enable across the fleet, and smoke the normal app screens on separate devices/networks within budgets. Update private Review Notes only after verification. Activation is not part of artifact creation or default implementation completion.
5. Rotation/disablement follow Decision 5. Rollback: disable the exception everywhere, revoke review refresh/recovery credentials, observe the residual access window, then redeploy the previous pinned image if required. Leave the additive table intact; older code ignores it and still uses ordinary email OTP. Do not delete or reset review content as rollback.
